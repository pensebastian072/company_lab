# B6 - the recount of overstated and stale totals

Run 2026-09-10. Advisory / SHADOW; `promoted` is false and nothing here touches a company
score, a ranking, or a verdict. Every figure below is recounted from the live store or
from a real test run, never from a report, a cache, or another document.

Corpus state for every count on this page: `CORPUS_SNAPSHOT_2026-09-10.json` on D: under
`external/reports` - 7,223 claims (7,099 `VERIFIED_LOCAL`, 65 `UNVERIFIABLE`, 59
`SELF_ATTESTED`), 311 companies with current research of a 1,500-row book, 74 live
industry objects of 109. Regenerate it with `scripts\corpus_snapshot.py`.

B6 was raised as item 6 of the 2026-09-07 backcheck: *"Several handoff totals and
validation claims are overstated or stale. Examples include E54 answered/UNKNOWN counts,
omitted custody risk endpoint, search counts conflated with repeated source reads, and
E57's test count taken from cached test identifiers."* Four examples. All four reproduce.

---

## 1. E54 answered/UNKNOWN - CONFIRMED, off by six

`E54_results.md` said E54 "answered 41 of 45 structural fields, and the four UNKNOWNs are
all argued refusals."

From the store, the 15 objects at version `2026-09-06`:

| | |
|---|---:|
| structural field values | 45 |
| UNKNOWN | **10** |
| answered | **35** |

The "four" counts **buckets, not fields**: `mortgage_reits` contributes one UNKNOWN field,
and the three incoherent buckets - `commercial_residential_mortgage_finance`,
`multi_sector_holdings`, `specialized_finance` - contribute three each. Four buckets, ten
fields.

The file contradicted itself in two places before anyone recounted: its own UNKNOWN
inventory lists all ten, and its own endpoint table uses denominators of 11, 12 and 12,
which sum to 35. **A number can be wrong in a document that already contains the right
one.** Corrected in place beside the original.

The interpretation does not move. Four argued refusals of buckets that did not hold
together is still the behaviour the prompt asked for, and the flat middle is still what
E58 was registered against.

## 2. The omitted custody endpoint - CONFIRMED

`E54_results.md` said **"E54 never uses the bottom of any scale"** and "no FLAT, no
DECLINING, no EXCEPTIONAL, no EXTREME, no SEVERE anywhere in the set."

`custody_banks.substitution_risk` is **LOW**. That scale is
`SEVERE -> ELEVATED -> MODERATE -> LOW`, written worst-first so that `normalized()`
returns 1.0 for LOW, which makes LOW a terminal value of the scale. Recounted: **1 of the
35 answered values sits at a scale endpoint**, not zero.

The mechanism is worth more than the correction. E54's table tested only the **adverse**
endpoint of each scale - DECLINING/FLAT, EXTREME, SEVERE - and then the prose generalised
to "any scale". The favourable endpoints (EXCEPTIONAL, and LOW on both risk scales) were
never counted, and one of them was in use. A one-directional measurement was reported as a
two-directional claim.

The substantive worry survives and is arguably sharper for being exact: **34 of 35
answered values are interior**, and 0 of 12 `replication_difficulty` values are EXTREME
across a set holding `financial_exchanges` and `diversified_banks`.

## 3. Searches conflated with source reads - CONFIRMED

E54 reported "the 68-search underrun against a 200-280 budget."

From the store, the 75 object claims behind those 15 objects cite:

| | |
|---|---:|
| distinct `source_url` | **35** |
| URLs cited more than once | 26 |
| repeat citations | 40 |

So slightly more than half of the claims rest on a re-read of a document another claim
already used. Sixty-eight is a measure of **work done**; the evidence base is **35
documents**. Both numbers are true and they answer different questions. Quote distinct
sources when the question is how much evidence there is.

This is the same shape as item 6 below: a count that reads as breadth but measures effort.

## 4. E57's test count from cached identifiers - CONFIRMED, and worse than one number

No count appears in `E57_results.md` itself. The stale counts live in the handoffs, and
there were **four different ones in the tree at once**:

| location | said | |
|---|---:|---|
| `HANDOFF.md` | 505 | stale |
| `HANDOFF.md` (command block) | 214 | stale |
| `CODEX_HANDOFF.md` (x2) | 329 | stale |
| `docs/HANDOFF_E54_FINANCIALS_PHASE_A.md` | 1,138 | true at `cfe83d8`, left as a dated receipt |

Recounted by running the suite on 2026-09-10:

```
1,329 collected, 1,329 passed, 0 failed, 0 skipped, 85 files
```

And the mechanism the audit named reproduces exactly: `.pytest_cache/v/cache/nodeids`
holds **1,395** node ids. That is **66 more tests than exist** - stale identifiers for
tests since renamed or deleted, which the cache never prunes. A count taken from the cache
overstates the suite by 5% and will drift further every time a test is renamed.

**Count from a run, never from the cache.** Corrected in place in both handoffs; the E54
handoff keeps its 1,138 because it is a dated receipt of a specific commit, which is the
one form of an old number that is not stale.

## 5. The Financials uniform-5 - NO LONGER TRUE, and that is the finding

`E78_results.md` asked for this one. E54 found all 15 new objects carrying exactly 5
claims, zero variance, against a 4-to-11 spread elsewhere.

Live claims-per-object histogram today:

| | |
|---|---|
| `financials` | 4:3, 5:13, 6:2, 7:2, 8:1, **15:1** |
| everything else | 4:6, 5:23, 6:2, 7:4, 8:4, 9:4, 10:4, 11:2, 16:1 |

The E56 re-cut and subsequent work broke the zero-variance shape. **The original finding
stands as a fact about one delivery and must not be quoted as a live property of the
Financials corpus** - which is precisely the failure mode B6 exists to catch, one step
removed.

## 6. Source concentration - the previous finding pointed at the wrong page

`SCORE_STALENESS_2026-09-09.md` flagged 33 claims resting on a single unreachable DOJ
press release. That URL now carries **34 claims across 18 tickers**.

But searching only where the last finding pointed would have missed the larger one:

| claims | tickers | source |
|---:|---:|---|
| **162** | **70** | one FDIC quarterly-banking-profile speech |
| 88 | 42 | one EIA Today-in-Energy page |
| 87 | 64 | `computed://company_lab/revenue_share` |
| 34 | 18 | the DOJ release already flagged |

Corpus context: 7,223 claims over **917 distinct URLs**, the ten most-cited carrying 656 =
**9.1%**. The corpus is not broadly concentrated. It has a few very load-bearing pages, and
the top two are single documents underpinning a whole sector's structural claims.

Whether that is a defect is **not settled here**. It is a question about scope
comparability - is one quarterly profile the right source for 70 companies at once - and
it is a different question from verification, which only asks whether the quote is on the
page.

---

## What this does and does not establish

It establishes that four named totals were overstated or stale, that all four are now
recounted from the store or from a run, and that the corrections sit beside the originals
rather than over them.

It establishes nothing about whether the research is right. Every verdict in this repo is
unchanged: E05's top decile still ran -7.6% median three-year excess against SPY, E03 still
puts 95.6% of ranking power in sector selection, and `promoted` is still false.

**The pattern across all six items is one thing.** Every wrong number here was a count of
*effort* or a count *from a cache*, read as a count of *evidence* or a count of *what
exists*: 68 searches read as 68 sources, 1,395 cached ids read as 1,395 tests, four buckets
read as four fields, one-directional endpoint avoidance read as "any scale". None of them
needed new data to catch - only a recount against the thing itself.
