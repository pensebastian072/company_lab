# V2 lane — the whole report, judged by LFM2.5-2.6B-Finance

Runbook for **Saturday 2026-08-29**. Written 2026-08-28 the night before.

**What this is.** A second, parallel company_lab that is identical to production in every
way except one: the judged half is generated by
`hf.co/mradermacher/LFM2.5-2.6B-Finance-GGUF:Q4_K_M` instead of `qwen2.5:7b`. Same rubric,
same evidence packs, same measured half, same scorecards, same Excel workbook. Ten
companies at a time, resumable, all day.

**What this is NOT.** Not a promotion, not a bake-off arm, not a validation. E07's criteria
are not being applied here and no model replaces another on the strength of it. `promoted`
stays false. The judged half has never been graded against forward returns in either lane,
so "better" remains unmeasurable — this produces a *comparison*, not a verdict.

---

## Why the measured half makes this clean

The measured half (FE 18, BS 10, VA 15, ER 5, EN 2) is deterministic and reads the same
EDGAR/yfinance caches on `D:`. Both lanes compute it **bit-identically**. So every
difference between the v1 and v2 workbooks is attributable to the judged half alone
(SG 20, BQ 15, MG's judged remainder). That is the one clean property this design has, and
it is worth not breaking.

## Four blockers, all of which must clear before the first batch

### B1 — the output path is hardcoded, and a v2 fold would overwrite production

`DATA_DIR = BASE_DIR / "data"` (`clab/config.py:27`) is **not** env-overridable, and it
owns `scorecards/`, `scores.parquet` and `exports/`. Running the v2 fold in this checkout
would overwrite the qwen judged half that the UI on :8100 reads and that every study
depends on. `CLAB_DATA_ROOT` only moves the `D:` bulk side.

**Fix — a second checkout, no code change:**

```
C:\Users\<your-user>\company_lab_v2      <- own data/, own journal/, own WRITE_LEASE
CLAB_DATA_ROOT=D:\company_lab_data <- SHARED: edgar, yf, prices, universe, GPU lease
```

Two properties fall out of this for free, and both are wanted:

- **The GPU lease is shared** (`GPU_LEASE = DATA_ROOT/".gpu_lease.json"`, taken by
  `scorer.run_batch` at `clab/qual/scorer.py:618`), so the v2 lane serialises against the
  12:15 production qual task automatically. Run with `--wait-for-gpu`.
- **The write lease is NOT shared** (`WRITE_LEASE` lives under `BASE_DIR/journal/flags`),
  which is correct — the two lanes write different files and must not block each other.

### B2 — `fold_qual` globs across cache keys, so it is model-blind

Cache *keys* already include the model — `sha1(pack | prompt_sha1 | QUAL_MODEL)` at
`clab/qual/scorer.py:415` and `:435` — so no file gets overwritten. But
`_cache_has_any_score` asks `QUAL_DIR.glob(f"{cik}_{component}_*.json")`
(`clab/runner/fold_qual.py:39`), which matches **every** model's payload for that CIK.
With a shared `qual/` directory the v2 fold would see qwen's scores.

**Fix — one line in `config.py`:**

```python
QUAL_DIR = Path(os.environ.get("CLAB_QUAL_DIR", str(DATA_ROOT / "qual")))
```

v2 points at `D:\company_lab_data\qual_lfm25`. Add it to the mkdir loop at the bottom.

### B3 — `num_predict=700` is the bug that produced the 77.8%

`QUAL_NUM_PREDICT = 700` (`clab/config.py:124`) is not env-overridable and was tuned to a
model that answers directly. LFM2.5 reasons in prose first — measured at **3,417
characters** — and was cut off before emitting any JSON. That is what the 77.8% parse
failure was: a token budget, not a judgement.

**Fix:** `QUAL_NUM_PREDICT = int(os.environ.get("CLAB_QUAL_NUM_PREDICT", "700"))`.

### B4 — structured output was built for the bake-off and never wired into the scorer

`prompts.schema_for()` and `ollama.chat(fmt=...)` exist (uncommitted, from today), but
`scorer.py:510` still calls `ollama.chat(prompt, system=...)` with neither `fmt` nor
`num_predict`.

**Fix:** pass `fmt=prompts.schema_for(component)` when `CLAB_QUAL_STRUCTURED=1`.
Env-gated, so the production lane stays bit-identical to today.

**Structured output is ON for this run, and that is a different call than the one for
E07.** In the bake-off, `--structured` would gut M2 as a discriminator — every arm scores
0.0% parse failure by construction. Here we are not running M2. We want usable scorecards,
and the schema makes a parse failure, a missing key and a prose preamble structurally
impossible while keeping `null` a legal score type, so honest abstention is never forced
into a fabricated number.

### One trap: none of B3/B4 is in the cache key

The key is `sha1(pack | prompt_sha1 | QUAL_MODEL)`. It does **not** include `num_predict`
or the structured flag. So changing either one mid-day silently mixes two generation
regimes into one dataset with no way to tell them apart afterwards. **Settle both before
the first batch and do not touch them again.** If they must change, wipe `qual_lfm25/` and
restart — cheap early, expensive late.

## Pick the sample before the run, not after it

At 3 generations per company, the only measured datapoint is **13.1 s/gen** — and that was
truncated output, so it is a floor. Raising the budget makes generation slower;
constraining to a schema makes it faster (no prose preamble is permitted). Net effect is
genuinely unknown, which is what the probe is for.

| if the probe says | per company | 10 take | ~12 h of GPU gets |
|---|---:|---:|---:|
| 15 s/gen | 45 s | 7.5 min | ~800 companies |
| 30 s/gen | 90 s | 15 min | ~400 companies |
| 45 s/gen | 2.3 min | 23 min | ~310 companies |

**Expect 300–900 of 1,501. Not all of them.** Which means the stopping point is arbitrary,
and *that* is the thing to design around:

> **Do not run in market-cap order and stop when the day ends.** That yields a
> large-cap-only sample, and every v1-vs-v2 comparison then confounds the model with size
> — on top of the 0.319 size tilt already entangled with the judged half.

Instead: **draw a fixed comparison set once, stratified across the 11 GICS sectors and 3
size terciles, and score it in a fixed shuffled order.** Then whatever fraction finishes is
still balanced, and a partial run is honest rather than skewed. Size it from the probe:
take the 12-hour estimate and register **60% of it**, so the set is likely to *complete*.

Register the set to `journal/experiments/E36_lfm25_v2_lane.md` before the first batch —
set size, seed, order, what will be compared, and the prior.

## The prior, stated before the run

From the E07 amendment, unchanged and still on the record: I expect the
**unverified-evidence rate to be worse** than qwen's 0.28%, because the tune rewards
confident answering, and I expect the **abstention rate to fall** — qwen sits at 78.3% mean
null on E12's four watched BQ dimensions. If abstention falls *without* unverified evidence
rising, that is the good surprise, and it means a quarter of the universe sits under the BQ
floor because of the model rather than the rubric (E12 P1). If both move together, it is
E07's standing finding again: every model that abstains less also fabricates more.

## Morning sequence

**Before anything: commit the loose bake-off work.** Six modified files and five untracked
E07 artifacts are sitting uncommitted — the `</think>` parser fix, the `--structured` /
`--num-predict` / `--components` flags, `prompts.schema_for`, and the amendment. The v2
lane builds directly on that code and it must not be mixed into the v2 diff.

| step | ~time | what |
|---|---|---|
| 1 | 5 min | **Preflight.** Ollama up, LFM2.5 present (1.7 GB, confirmed), GPU free, 03:00 crawl finished clean, `D:` free (181 GB, ample). Check whether the crawl invalidated qual cache keys. |
| 2 | 10 min | **Commit the bake-off work** in `company_lab`, then create the `company_lab_v2` checkout at the same commit. |
| 3 | 15 min | **Apply B1–B4** in the v2 checkout. Run the test suite there — 779 green is the bar. The three env knobs default to today's behaviour, so a green suite proves the production lane is untouched. |
| 4 | 20 min | **Probe: 10 companies, timed.** Read s/gen, parse-failure rate, null rate, and eyeball three scorecards for prose leaking into a rationale field. This is the go/no-go. |
| 5 | 10 min | **Register E36** — sample size from the probe, seed, order, comparison, prior. Draw the stratified set. |
| 6 | rest of day | **Batches of 10, resumable**, checkpointed after each, `--wait-for-gpu`. Status to `journal/runs/v2_lfm25_<date>.log`. |
| 7 | 30 min | **Fold → export → diff.** v2 workbook, then the comparison report. |

Steps 1–5 are about 60 minutes. First real batch lands roughly an hour after you sit down.

### The probe is a gate, not a formality

Kill the day at step 4 and re-think if any of these:

- parse failures still above ~5% **with** the schema constraint (means the schema is not
  being honoured, not that the model is bad),
- `null` rate at or near 0.0% across the board (the tune is answering everything, which
  makes the judged half confident noise — check unverified evidence immediately),
- rationale text that does not match the evidence pack (fabrication; the failure mode the
  model card predicted),
- projected 12-hour throughput under ~150 companies (the sample gets too small to say
  anything, and the day is better spent elsewhere).

## Commands

```powershell
# --- step 2: the v2 checkout, at the same commit ---
git -C C:\Users\<your-user>\company_lab worktree add C:\Users\<your-user>\company_lab_v2 HEAD --detach
# (a plain clone works too; the worktree shares .git and costs no extra disk)

# --- the v2 environment, set once per shell ---
$env:CLAB_QUAL_MODEL       = "hf.co/mradermacher/LFM2.5-2.6B-Finance-GGUF:Q4_K_M"
$env:CLAB_QUAL_DIR         = "D:\company_lab_data\qual_lfm25"
$env:CLAB_QUAL_NUM_PREDICT = "2500"
$env:CLAB_QUAL_STRUCTURED  = "1"
$env:CLAB_DATA_ROOT        = "D:\company_lab_data"   # shared caches + shared GPU lease
$env:CLAB_UI_PORT          = "8101"                  # if the v2 UI is ever started

# --- step 4: the probe ---
cd C:\Users\<your-user>\company_lab_v2
.venv\Scripts\python.exe -m clab.runner.batch --symbols <10 tickers> --wait-for-gpu

# --- step 6: one batch of ten, resumable ---
.venv\Scripts\python.exe -m clab.runner.batch --symbols <next 10> --wait-for-gpu

# --- step 7: fold and export ---
.venv\Scripts\python.exe -m clab.runner.fold_qual
.venv\Scripts\python.exe -m clab.export.refresh
```

Batches of 10 also stay under the probe gate that refuses runs over 50 symbols without a
fresh probe — the same gate that silently refused a 99-company fold on 2026-08-16. Ten at a
time never trips it.

**One `--symbols` warning from `CLAUDE.md`:** re-scoring by name used to rewrite a company's
*profile* when the ticker was missing from the tier being searched. It searches every tier
now, but the log line `taking its classification from` is the tell. If it appears in the v2
log, that company's sector profile was reassigned and its coverage is not comparable to
v1's.

## What comes out at the end

1. **`company_lab_latest.xlsx` in the v2 checkout** — the same 11 sheets, judged by LFM2.5.
2. **A diff report** against v1 over the same companies:
   - judged-half point delta per company, and the band moves it causes,
   - abstention rate per BQ dimension against qwen's — E12's four watched dimensions
     (`network_effects`, `manufacturing_complexity`, `data_advantages`,
     `economies_of_scale`) are the number this exists to move,
   - coverage change, and how many companies cross or fall below the 0.80 band gate,
   - unverified-evidence rate, measured on real production output instead of a
     9-generation smoke test.
3. **E36 written up** — including, if it comes to it, that the model is worse. A failure
   written down is the point.

**Nothing here promotes anything.** Both lanes remain an LLM's judgement with no human
review step, on a score whose top decile underperformed SPY at the median over 3 years
(E05). The v2 workbook is not a second opinion to trade on; it is a measurement of how much
of the judged half is the *model* rather than the framework.
